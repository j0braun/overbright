The same 104 objects every time (Mesa's blob: each object 12 + 32 key bytes, its data aligned to 8 from the
Vulkan header; 22 of the 104 data sizes are 4 mod 8), so the order the hash table writes them in sets the padding:
a run that adds nothing can come out 4 bytes longer than the file it read. With SUBGROUP 55 of the 104 keys
differ (the stage flag), and a run reading the 108944 file serialised 108948: written again, step 2 failed
(gate runs 2 of 2, and r2 / r4 of four manual pairs). Each object also carries one byte that differs per process,
so the rewritten file is not byte-equal either.
